Architecture and ownership 

Dagster schedule: 03:00 / 15:00 Pacific/Auckland
  → isolated local news runtime
  → public feeds → evidence → article analysis/review
  → event comparisons → editorial selection → summary review
  → validated reader-only export → privacy scans → site-only main commit
  → GitHub Actions → GitHub Pages
  → delivered hashes verified → immutable PostgreSQL publication receipt

The existing Dagster instance owns scheduling, launch history and retries. The model service and news PostgreSQL database remain private. One Dagster operation wraps the retained Python workflow; PostgreSQL owns its detailed processing checkpoints. This avoids maintaining two competing stage-retry systems.

The news code location has its own Python environment, settings and worker service. Two global run slots with one per code location preserve the original location’s one-run limit while allowing news to progress independently. The original property code-server PID was unchanged during validation.

These are retained stage timestamp windows, not additive CPU measurements. The complete 152.1-minute run includes processing, export, deployment and confirmation. This is one cold benchmark at 232 articles; expanding the feed catalogue requires another capacity measurement.

Attempts retain a stable run UUID and commit. Detached publishing worktrees keep an abandoned push from blocking later runs. Disjoint reviewed code updates can fast-forward while preserving an export; this path was also exercised by the actual build spanning a reviewed main update. The job has a three-hour subprocess limit, two retries five minutes apart, a whole-publication database lock and a twenty-minute delivery-verification window. Generation failure leaves the last good edition available.

Runtime code is pinned to a reviewed revision. Code/design changes require a deliberate local rollout alongside their release; routine generation updates only site/ . A space-free service alias avoids service-path parsing problems while runtime storage stays on the local SSD. Recovery commands and ownership are in operations documentation .

Seven verified merged remote feature branches were retired. Their private authoring worktrees were preserved. The remaining update branches belong to active Dependabot PRs, not unfinished feature work. Dependabot’s first Python and GitHub Actions checks succeeded; security alerts and security-update PRs are enabled, with reviewed updates and no auto-merge.

Automatic publication uses a repository-specific SSH deploy key. Export paths are explicitly restricted, files and outgoing commits pass fully redacted Gitleaks, and reader fields reject private network/filesystem information. The developer release also received a manual infrastructure-label, address, hostname, path and personal-information inspection. Detailed diagnostics, settings, retrieved text, model responses and screenshots remain private. Credential scanning alone does not establish complete publication safety.

Practical limits

Model self-review is not independent fact checking. The delivered stories include direct source links and dates, and ambiguous outcomes are withheld. No physical power-loss test or multi-day uptime study was performed. GitHub cron timing is best effort; periodic dispatch itself was not observed during this validation, although stale/healthy watchdog execution and issue recovery were verified. The local schedule was tested through a real due tick. Browser checks used Chromium; Safari and screen-reader behavior were not tested in this release.

This report contains measured results and public release identifiers. It intentionally omits private infrastructure details and raw processing logs.
